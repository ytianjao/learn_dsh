# 变更日志 / Changelog

- **Current docs now have one answer per rule, and CI catches version drift.** `docs/UPSTREAM_COMPATIBILITY.md`, `docs/ACCEPTANCE_SCENARIOS.md`, and `docs/WEB_ACCEPTANCE.md` each carried copies of five or six `docs/PRODUCT_CONTRACT.md` sections that had already diverged from it — one still said only completed Tasks unlock the next, and two repeated the foreign-session redaction that no code implements. The copies are replaced by a link, and the acceptance-specific sections lose two claims the code contradicts. In `PRODUCT_CONTRACT.md`, rules the code no longer follows — the PR #13 empty-plan flow, v1 migration, the unused inline-checkpoint range, and the rc.8 schema-rewriting deny-list — move to a History section marked as not current, and the Hard-gate contradiction about `studied` dependencies is fixed. Several docs claimed the installed Harness was `0.2.1-alpha.1` while the lockfile installs `0.2.1-alpha.4`; they now name the floating peer range and point at `pnpm-lock.yaml`. New `tests/doc-facts.spec.ts` fails, naming file and line, when a current doc cites a missing `pnpm run` script, a caret range that differs from `package.json`, a pinned prerelease Harness version, a stale epoch, or a compatibility row that differs from `package.json`. / **现行文档每条规则只有一个答案，版本漂移由 CI 捕获。** `docs/UPSTREAM_COMPATIBILITY.md`、`docs/ACCEPTANCE_SCENARIOS.md` 与 `docs/WEB_ACCEPTANCE.md` 各自复制了 `docs/PRODUCT_CONTRACT.md` 的五到六个章节，且已与原文分叉——其中一份仍写着只有已完成的任务才能解锁下一任务，两份重复了没有任何代码实现的异源 Session 脱敏投影。这些副本改为链接，验收专属章节中与代码矛盾的两处说法也已修正。`PRODUCT_CONTRACT.md` 中代码已不再遵循的规则——PR #13 的空计划流程、v1 迁移、未使用的 inline-checkpoint 范围、rc.8 改写 schema 的 deny-list——移入标明非现行的“历史说明”，并修正了关于 `studied` 依赖的 Hard gate 矛盾。多份文档声称已安装的 Harness 是 `0.2.1-alpha.1`，而 lockfile 实际安装的是 `0.2.1-alpha.4`；现在改为写浮动的 peer 范围并指向 `pnpm-lock.yaml`。新增的 `tests/doc-facts.spec.ts` 会在现行文档引用不存在的 `pnpm run` 脚本、与 `package.json` 不一致的 caret 范围、写死的预发布 Harness 版本、过时的 epoch 或与 `package.json` 不一致的兼容表行时失败，并指出文件与行号。
- **The state projection no longer sends the active Project twice.** `projectState()` returned the whole `workspace` and, beside it, `activeProject` — the same object already present in `workspace.projects`. Measured on a freshly started interview, the duplicate was 4,602 of 9,955 bytes (46%) of every state read and every mutation response. The top-level `activeProject` field is gone; the client reads `workspace.projects[workspace.activeProjectId]` through one helper, `activeProjectOf`, at all nineteen former call sites. This is a breaking change to the HTTP v3 response shape with no alias: the client and Host ship in one package, so no other consumer exists. The persisted state is unchanged. / **状态投影不再重复发送当前 Project。** `projectState()` 既返回完整的 `workspace`，又在旁边返回 `activeProject`——而它就是 `workspace.projects` 里已有的同一个对象。在刚开始访谈的状态上实测，重复部分占每次状态读取与每个变更响应的 4,602 / 9,955 字节（46%）。顶层 `activeProject` 字段已删除；客户端在原先十九个调用点统一通过 `activeProjectOf` 读取 `workspace.projects[workspace.activeProjectId]`。这是 HTTP v3 响应形状的破坏性变更，不保留别名：客户端与 Host 同包发布，不存在其它消费者。持久化状态不变。
- **The mutation API enforces the boundary its contract already promised.** `docs/PRODUCT_CONTRACT.md` promised same-origin writes, a JSON content type, a dedicated mutation header, and a 128 KiB limit, but `body()` accumulated every chunk with no ceiling and no request was checked at all. Verified against the installed Harness first: DSH's web server registers routes and serves assets, and its `origin` is the bound address read back as a URL while its only `content-type` use is the gzip filter — it provides no CSRF check, no body ceiling, and no 413, so LearnLoop owns these guards itself. New `src/request-boundary.ts` validates the content type and the `x-learnloop-mutation: learnloop-v3` header *before* the body is read, refuses a foreign or `null` `Origin`, and streams the body under a hard 128 KiB count so a chunked request or a lying `Content-Length` cannot slip past a header check; an over-limit request stops accumulating immediately and returns 413 without mutating anything. Because the header is non-simple, a cross-origin `fetch` must preflight before it can send it, and this server never grants one. The degraded storage-recovery handler uses the same boundary, and the client sends the header on all three mutation call sites. The contract also loses two stale promises that no code implemented and that contradicted the Workspace model: the "server-redacted projection to foreign sessions" and the owner-session-only backup. `/ **变更接口开始执行它早已承诺的边界。** `docs/PRODUCT_CONTRACT.md` 承诺同源写入、JSON content type、专用 mutation header 与 128 KiB 上限，但 `body()` 会累积全部 chunk 且没有任何上限，也没有任何请求被校验。先对已安装的 Harness 做了验证：DSH 的 web server 只负责路由注册与静态服务，它的 `origin` 是绑定地址回读成的 URL，唯一的 `content-type` 用途是 gzip 过滤——没有 CSRF 校验、没有 body 上限、没有 413，因此这些守卫由 LearnLoop 自己承担。新增的 `src/request-boundary.ts` 在**读取 body 之前**校验 content type 与 `x-learnloop-mutation: learnloop-v3`，拒绝异源或 `null` 的 `Origin`，并对字节流施加硬性 128 KiB 计数，使 chunked 请求或伪造的 `Content-Length` 无法绕过头部检查；超限请求立即停止累积并返回 413，不产生任何 mutation。由于该 header 属于非简单头，跨源 `fetch` 必须先通过预检才能发送，而本服务从不批准预检。降级态的 storage-recovery handler 复用同一道边界，客户端三处 mutation 调用点都会发送该 header。契约同时删除两条无实现、且与 Workspace 模型冲突的旧承诺："向异源 Session 返回服务端脱敏投影"与"仅属主 Session 可导出备份"。**

- **DSH now comes from npm; there is no source checkout to keep on disk.** The twelve `@deepseek-ai/*` devDependencies no longer point at a sibling `../deepseek-harness` clone — they are registry ranges, and `npx @deepseek-ai/dsh@alpha` runs the Harness. The peer strings moved from the exact `0.2.1-alpha.1` pin to the floating `^0.2.1-alpha.1` (and Cordis `4.0.2` → `^4.0.5-alpha.1`, matching what the published CLI actually depends on), because the Host's preflight validates peers with `semver.satisfies(runtime, range, {includePrerelease:true})`: an exact pin is denied the moment DSH moves, so a floating range is what lets the plugin follow the release without a code change. `scripts/verify-dsh-baseline.mjs` — whose every assertion enforced the checkout, including an explicit ban on registry-resolved DSH packages — is replaced by `scripts/verify-dsh-compat.mjs`, which calls the Host's own `evaluatePluginCompatibility` from `@deepseek-ai/dsh-app-boot` so the smoke test and the production gate cannot drift. The `setup-dsh` composite action, `scripts/dsh-baseline.json`, the baseline emitter, and `tests/dsh-baseline-outputs.spec.ts` are deleted; CI no longer stages a checkout. Verified against a real install: one npx tree carries all eleven peer packages, and the Host's module-resolution interception routes a linked plugin's bare `@deepseek-ai/*` imports to the launching installation, so plugin and Host still share one physical module copy. / **DSH 改为从 npm 安装，硬盘上不再保留源码检出。** 十二个 `@deepseek-ai/*` 开发依赖不再指向同级的 `../deepseek-harness` 克隆，而是 npm 版本范围；运行 Harness 用 `npx @deepseek-ai/dsh@alpha`。peer 从精确的 `0.2.1-alpha.1` 改为浮动 `^0.2.1-alpha.1`（Cordis 由 `4.0.2` 改为 `^4.0.5-alpha.1`，与发布版 CLI 的实际依赖一致），因为 Host 的 preflight 用 `semver.satisfies(runtime, range, {includePrerelease:true})` 校验 peer：精确 pin 在 DSH 一升级就会被拒绝，浮动范围才让插件无需改代码即可跟随发布。每条断言都在维护源码检出的 `scripts/verify-dsh-baseline.mjs`（其中一条还明令禁止从 npm 解析 DSH 包）被 `scripts/verify-dsh-compat.mjs` 取代，后者直接调用 Host 自己的 `evaluatePluginCompatibility`（来自 `@deepseek-ai/dsh-app-boot`），使冒烟测试与生产门禁不会漂移。删除 `setup-dsh` composite action、`scripts/dsh-baseline.json`、基线导出脚本与 `tests/dsh-baseline-outputs.spec.ts`；CI 不再准备任何检出。已用真实安装验证：一份 npx 安装树包含全部十一个 peer 包，Host 的模块解析拦截会把链接插件的裸 `@deepseek-ai/*` 导入路由到启动它的那份安装，因此插件与 Host 仍共享同一份物理模块。

- **The learning session no longer re-sends its prompt on every step.** DSH appends a changed system prompt to the cached history, and LearnLoop's section changed on every step, so one 6-turn session carried 12 system copies (about 145k characters, roughly 57% of the last request's 61k input tokens). The section is now static (`LEARNLOOP_RUNTIME_V10`: the fixed policy and every phase policy, keyed by phase); the changing state is a compact runtime-context block (`LEARNLOOP_STATE_V1`, about 1.5k characters while teaching instead of about 8.6k) that DSH appends only when its text changes. In the keyless E2E every interview request now has one system message, and the state block is appended only when the phase changes. / **学习会话不再每一步都重发提示词。** DSH 会把变化后的系统提示词追加到已缓存的历史后面，而 LearnLoop 的分区每一步都在变，导致一次 6 轮会话累积了 12 份系统提示词（约 14.5 万字符，占最后一次请求 6.1 万输入 token 的约 57%）。现在系统分区保持不变（`LEARNLOOP_RUNTIME_V10`：固定规则加按阶段列出的全部阶段规则）；变化的状态放进精简的运行时上下文块（`LEARNLOOP_STATE_V1`，讲解阶段约 1.5k 字符，原先约 8.6k），只有文本变化时 DSH 才追加。在无密钥 E2E 中，访谈的每次请求都只有一条系统消息，状态块只在阶段切换时追加。
- **The interview question travels in tool results only.** `questionToken` may be omitted (the Host asks its current question), every result returns the recorded `answer` with the `nextQuestion` contract, and exclusive codes are marked `relabel:false`, so the model stops relabeling "none" in every interview. / **访谈题目只通过工具结果传递。** `questionToken` 可以省略（Host 提出当前题目），每次结果都返回刚记录的 `answer` 与下一题契约 `nextQuestion`；互斥编码标记为 `relabel:false`，模型不再每场访谈都去改写“完全没接触过”。
- **The full plan is read on demand.** New read-only tool `learnloop_get_plan` returns the active plan as a complete Plan Intent; the runtime context keeps only the current task, upcoming task titles, and whether an adjustment is pending. / **完整计划改为按需读取。** 新增只读工具 `learnloop_get_plan`，返回可直接复用的当前计划意图；运行时上下文只保留当前任务、后续任务标题以及是否有待处理调整。
- **Tool declarations stay fixed for a learning session.** Hiding LearnLoop tools per phase rewrote the provider's tool list and broke its prefix cache (one interview step went from about 20k cached tokens to 3.5k). Every LearnLoop tool is now declared throughout; a call the phase does not allow is rejected before it runs with `INVALID_PROJECT_PHASE` (`refresh-state`), reading live state. / **学习会话的工具声明保持不变。** 按阶段隐藏 LearnLoop 工具会改写提供方的工具列表并打断前缀缓存（某次访谈步骤的缓存命中从约 2 万 token 跌到 3.5k）。现在全程声明全部 LearnLoop 工具；当前阶段不允许的调用会按实时状态在执行前以 `INVALID_PROJECT_PHASE`（`refresh-state`）拒绝。
- Smaller fixes: `requiredTools` lists only tools a step must call (teaching no longer names plan adjustment as required); tool results no longer show plan ids, and the policy forbids showing internal identifiers to the learner; lessons end by offering "check" and "skip the check" neutrally instead of always pushing the check. / 其它修复：`requiredTools` 只列出当前步骤必须调用的工具（讲解阶段不再把计划调整标为必需）；工具结果不再显示计划 id，规则也禁止向学习者展示内部标识符；课程结尾以中立方式同时提供“检查”和“跳过检查”，不再每次都催促检查。

- **Breaking epoch: state schema 19, Storage Domain 16, backup format 13.** Use **清除旧数据 / Clear old data** in LearnLoop, or clear the domain by hand; there is no migration. / **破坏性 epoch：状态 schema 19、Storage Domain 16、备份格式 13。** 请使用 LearnLoop 中的 **清除旧数据 / Clear old data**，或手动清理；不提供迁移。
- **The check is optional.** "学完了，跳过检查 / Done, skip the check" sits beside the check button while teaching, while a check is armed, and after a needs-work result. The Task becomes `studied` (new task status and execution phase): the next Task unlocks, but no assessment, evidence, or mastery is written and no article is generated. "补做检查 / Take the check" makes it current again later. / **检查变为可选。** 讲解中、检查已武装时以及评估未通过后，检查按钮旁都有“学完了，跳过检查”。任务变为 `studied`（新的任务状态与执行阶段）：下一任务解锁，但不写评估、证据或掌握度，也不生成课文。之后可通过“补做检查”让它重新成为当前任务。
- **A question during a check is answered, not graded.** New verifier tool `learnloop_release_check` returns a captured question, request, or off-topic message to teaching without an assessment or a counted attempt. / **检查期间的提问会被回答而不是评分。** 新增评测工具 `learnloop_release_check`，把被捕获的提问、请求或无关消息退回讲解，不写评估、不计尝试次数。
- **Learner questions can grow the plan.** `LEARNER_QUESTION_POLICY_V1` has the model answer first, then propose a plan adjustment only when the question shows an uncovered need; the learner still approves it in the Plan view. Runtime prompt V9 adds `activePlan` (the active plan as a copyable intent, task statuses, and whether an adjustment is pending), without which the model could not resubmit the whole plan. / **学习者的提问可以扩展计划。** `LEARNER_QUESTION_POLICY_V1` 要求模型先回答，只有问题暴露出未覆盖的需求时才提议计划调整；仍由学习者在计划视图中批准。运行时提示词 V9 新增 `activePlan`（可复用的当前计划意图、任务状态、是否有待处理调整）——此前模型无法提交完整计划。

- **The check question is shown where the learner answers.** "检查当前学习 / Check current learning" arms the check over HTTP and sends no chat message (the next learner message is captured as the answer), and the task's `checkPrompt` was only rendered inside the Plan view, so a learner in the chat saw a disabled "Answer in chat" button and no question. The launcher beside the composer now opens the question in a popover while the check is armed. / **检查问题显示在学习者作答的位置。** “检查当前学习”只通过 HTTP 武装检查、不发送聊天消息（下一条学习者消息即被捕获为答案），而任务的 `checkPrompt` 只在计划视图中渲染，导致停留在对话中的学习者只看到禁用的“请在对话中回答”按钮却看不到问题。现在检查武装期间，输入区旁的启动器会以浮层展开该问题。

- **A stale stored state no longer stops `dsh web`.** After an epoch bump DSH refused to open `learnloop.json` (`version-mismatch`) and `apply` threw, taking `dsh web` down until the file was moved by hand. LearnLoop now starts degraded: its routes answer `503 STORAGE_EPOCH_INCOMPATIBLE` with the stored and expected versions, and the panel and Settings offer **清除旧数据 / Clear old data**, which moves the file to `$DSH_HOME/learnloop/stale-backups/` (never deletes it), opens a fresh domain, and resumes without a restart. Nothing happens without that click. / **旧版本的存储状态不再导致 `dsh web` 启动失败。** 此前 epoch 升级后 DSH 拒绝打开 `learnloop.json`（`version-mismatch`），`apply` 抛错使 `dsh web` 无法启动，只能手动移走文件。现在 LearnLoop 以降级模式启动：其路由返回 `503 STORAGE_EPOCH_INCOMPATIBLE` 并附带已存与期望版本，面板和设置页提供 **清除旧数据 / Clear old data**，点击后把文件移到 `$DSH_HOME/learnloop/stale-backups/`（不删除）、打开新的存储域并直接恢复，无需重启。不点击就什么也不会发生。
- **Clearing a learning plan also deletes its lesson files.** `clear-project` now removes `$DSH_HOME/learnloop/content/ws-…/project-…` after the state commit and reports `contentRemoved`; exports saved elsewhere are kept. / **清空学习计划时一并删除课文文件。** `clear-project` 在状态提交后删除 `$DSH_HOME/learnloop/content/ws-…/project-…` 并返回 `contentRemoved`；保存在其它位置的导出文件保留。
- **A read-only learner's plan no longer fails in a loop.** The mode gate rejected every `apply` task when `practiceCapacity` was `none`, but the model was never told that rule and the `INVALID_PLAN` error dropped its reason, so `learnloop_create_plan_draft` failed three times with "LearnLoop could not complete this operation." The planning and active host-control JSON now publishes `planConstraints` derived from the confirmed Profile, and `INVALID_PLAN` carries `details.violation` naming the rule and the offending tasks. / **只看不练的学习者生成计划不再反复失败。** 当 `practiceCapacity` 为 `none` 时，模式门禁会拒绝所有 `apply` 任务，但模型从未被告知这条规则，且 `INVALID_PLAN` 错误丢弃了原因，导致 `learnloop_create_plan_draft` 连续三次只得到 “LearnLoop could not complete this operation.”。现在规划与执行阶段的 host-control JSON 会发布由已确认档案推导的 `planConstraints`，`INVALID_PLAN` 也会在 `details.violation` 中写明违反的规则与相关任务。
- **Breaking epoch: state schema 18, Storage Domain 15, backup format 12, profile interview schema 5.** Clear only LearnLoop domain data or use an isolated `DSH_HOME`; there is no migration. / **破坏性 epoch：状态 schema 18、Storage Domain 15、备份格式 12、访谈 schema 5。** 请仅清空 LearnLoop 域数据或使用隔离的 `DSH_HOME`；不提供迁移。
- **The baseline interview shrinks from 14 questions to 5 (6 with hands-on practice).** Only answers the plan needs are asked: subject, outcome, experience, learning style, and weekly time, plus practice constraints when the learner wants hands-on practice. One learning-style question replaces the separate learning-mode and practice-capacity questions and sets both plan gates. The starting level and success criteria are derived (`host-derived`) from experience and outcome; resources, knowledge gaps, time pattern, deadline, and example preference become optional Probes that stay `null` (`not-asked`) unless asked — no default stands in for an answer. / **基线访谈从 14 题缩减为 5 题（选择动手练习时 6 题）。** 只问计划真正需要的：学习主题、期望目标、相关经验、学习方式、每周时间，选择动手练习时再问练习限制。一道“学习方式”题取代原来的学习方式与实践能力两题，并同时决定两项计划约束。当前基础与成功标准由经验和目标推导（`host-derived`）；已有资源、知识缺口、时间安排、期限、示例偏好改为可选题，未询问时为 `null`（`not-asked`）——不再用默认值冒充学习者的回答。
- **The model adds optional Probes when the learner's words give a reason.** `learnloop_ask_profile_question` accepts `addProbes` (from `currentQuestion.optionalProbes`, at most 4 per interview); added Probes are asked next and remain Host-defined, so their answers are canonical. / **当学习者的话给出理由时，模型可以追加可选题。** `learnloop_ask_profile_question` 新增 `addProbes`（来自 `currentQuestion.optionalProbes`，整场最多 4 道）；追加的题紧接着提问，仍由 Host 定义，因此答案依旧是规范编码。
- **Any Profile field can be edited in review.** `revise-profile-field` changes one field with the Host options of its Probe — including fields that were never asked — raises the Profile revision, and records a learner revision; derived fields follow their source until edited directly. The review dialog has an inline editor per row. / **审阅页可以修改任一字段。** `revise-profile-field` 用对应题目的 Host 选项修改单个字段（包括未询问的字段），提升档案修订号并记为学习者修改；推导字段在被直接修改前会随来源字段更新。审阅弹窗的每一行都有内联编辑器。
- **The interview is a Host-defined pipeline that a "null model" can complete.** Every Probe declares its kind, single- or multi-select cardinality, option codes, exclusive options, and Profile mapping (`docs/PROFILE_INTERVIEW.md`). Multi-select questions are now asked as multi-select and every choice is kept; Profile lists hold `{code, label, source}`; "nothing" is a code rather than a resource string; deadlines are structured; example density is high only when the learner picks `example-rich`. No Chinese word list or regex interprets option text any more. `target-outcome.quality-bar` is merged into the success criteria. / **访谈成为由 Host 定义、“空模型”也能走完的管线。** 每道题声明类型、单选/多选、选项编码、互斥项与画像映射（见 `docs/PROFILE_INTERVIEW.md`）。多选题现在以多选提问并保留全部选择；画像列表保存 `{code, label, source}`；“什么都没有”是一个编码而非资源文字；期限为结构化值；只有学习者选择 `example-rich` 才会提高示例密度。不再用中文词表或正则解读选项文字。`target-outcome.quality-bar` 并入成功标准。

The Host validates keys, sizes, uniqueness, dependency references and DAG shape, then assigns IDs/status/version and commits plan, mastery, events, and one revision atomically.

User flow: (1) configure and select a model in **DSH Settings → Models**; (2) enter a LearnLoop goal; (3) choose **Start learning**; (4) observe the planning request in Chat; (5) the model calls `learnloop_publish_plan`; (6) the model introduces the returned first task; (7) choose **Start task in chat** for teaching; (8) submit your own evidence in LearnLoop; (9) export before using **Discard current plan** to start over. Normal `dsh web` uses the selected user model; only browser E2E uses the deterministic mock provider.

DSH owns session, Chat, model routing, streaming, credentials, and the tool execution runtime. LearnLoop owns the learning project, validated structured plan, evidence, mastery, review, and plan-publication rules. Discard is destructive, not history archival: it removes current business data while preserving settings. Export first when an audit copy is required.

## Runtime hardening (PR #20)

A LearnLoop project is bound to exactly one DSH Session. The Host returns a server-redacted projection to foreign sessions and rejects their project mutations; this local product-state isolation prevents accidental cross-session access, but is not multi-user or multi-tenant authentication. Same-origin remains the HTTP write boundary and LearnLoop never receives model credentials.

Task status changes are available only through semantic commands: start, pause, resume, skip, safe restore, and atomic completion with evidence. A blocked task remains the current learning position; only completed or skipped dependencies are satisfied, and skipping never means mastery. Completing a task does not auto-start its successor.

Invariants: `project.sessionId === mutation.sessionId`; active and blocked current tasks cannot coexist; `foreign => no project, plan, evidence, mastery, assessment, adjustment, or event content`.

## Current LearnLoop interaction protocol

Activation is Host-owned: button → HTTP `begin-learning-mode` → `interviewing` Project → visible learner intent. The agent interviews, commits and obtains explicit Profile confirmation, creates a Draft Plan, and asks the learner to **确认并启用计划 / Confirm and activate plan**. After confirmation the Plan is active, execution is null, and all Tasks remain pending. Teaching starts only after the learner explicitly starts the first Task in LearnLoop. LearnLoop phase policy and domain guards reject wrong-phase model calls with `INVALID_PROJECT_PHASE`; model-visible outputs use semantic fields such as `profileRevision`, `planId`, and `planVersion`, never a generic workspace revision.
